## 1. Overview

This document is the authoritative reference for trimming the AMS (Amoro Management Service)
metrics surface. It is intended to drive a concrete development task: **introduce a
field-level whitelist mechanism so that AMS can ship a smaller default metric footprint
without breaking existing dashboards or APIs**.

- **What this document covers**: every metric currently registered by AMS, grouped by
  source class, with a per-metric retention judgement, the proposed configuration model,
  the minimum source-code change set, and a quantitative before/after comparison.
- **Audience**: developers implementing the change, reviewers validating the trimming,
  and SREs who decide which knobs to flip in production.
- **How it is organised**:
  - §2 inventories every metric in AMS today.
  - §3 groups metrics by purpose and gives the keep / drop verdict.
  - §4 specifies the whitelist mechanism (config + code skeleton).
  - §5 quantifies the savings.
  - §6 lays out the development plan, risks and rollout.
  - §7 is the explicit acceptance checklist for the implementer.

> **Cross reference.** The earlier per-table memory analysis (`TableOptimizingMetrics`
> 21 metrics × 100k tables ≈ 756 MB) is the motivating context; it is **not**
> re-derived here. See the previous analysis turn for the raw arithmetic.

#### 2.3.1 Profile-level retention quick reference

The table below cross-references every metric in this class against the three
pre-baked profiles. Source of truth: `RECOMMENDED_OPTIMIZING` / `MINIMAL_OPTIMIZING`
/ `LEGACY_OPTIMIZING` in `MetricFilterConfig.java`. See §3.3 / §3.4 / §3.5 for the
verdict rationale and §4.4 for the unified profile table.

> **Status sub-group selection rationale (Revision 2026-06-02 follow-up).** With
> the value-based filter `metric.optimizing.skip-zero-status` + per-state
> `metric.optimizing.status-duration-threshold-mills.<state>` already in place,
> the four active-stage `status_*_duration_mills` gauges (pending / planning /
> executing / committing) strictly subsume the corresponding `status_in_*`

> an idle gauge can opt back via `legacy` or `custom`. The actual emitted

## 3. Grouping & Trimming Verdict

This chapter splits the inventory into seven semantic groups that match the way operators
actually use the metrics. For each group the verdict is one of:

- **MUST KEEP** — high operational value, keep registered by default.
- **OPTIONAL** — useful but redundant or rarely consulted, off by default, opt-in.
- **DROP** — strictly redundant with another retained metric, off by default.

Per-table metrics dominate footprint, so trimming priority is highest there.

### 3.1 Group P (Process / JVM) — A1..A8

This group covers AMS process health. Cardinality is constant (≤ 8 + 2 × #GCs).

- **Verdict: ALL MUST KEEP**. Memory cost is negligible (a handful of metrics per process)
  and JVM-level alarms (heap pressure, GC time, thread leak) are essential.
- No trimming knob is required for this group; the whitelist mechanism in §4 simply
  always allows it.

### 3.2 Group Q (Optimizer Group) — G1..G10

This group covers per-optimizer-group queue/resource state. Cardinality = #groups
(typically < 100 even in large deployments).

- **MUST KEEP — G1, G2, G4, G5, G7, G8, G9, G10** (8 metrics): tasks queued, tasks
  running, tables pending / executing / committing, optimizer instance count, memory,
  threads — all directly drive scheduling alarms and capacity planning.
- **OPTIONAL — G3 (`planing_tables`), G6 (`idle_tables`)**: the planning state is short
  and noisy; the idle count is implicitly `total_tables - others`. Keep registered by
  default but exposed in the whitelist so they can be dropped when group cardinality
  matters (e.g. very large deployments with many groups × many AMS instances).
- **No DROP**.

### 3.3 Group R (Per-table Optimizing Status) — O1..O10

This group expresses **"what status is the table in right now"** in 10 metrics that are
mutually redundant (5 status-duration gauges + 5 status-indicator 0/1 gauges; at any
moment 4 of each subgroup are zero).

**Operational principle (Revision 2026-06-02).** With the value-based filter
`metric.optimizing.skip-zero-status` + per-state `status-duration-threshold-mills.<state>`
in place, each duration is registered with the `MetricRegistry` only when it actually
exceeds the operator-configured threshold. Under that filter, durations strictly
dominate indicators on every axis:

- **Expressiveness**: `duration > 0 ⇔ in_state == 1`, and the duration value
  additionally carries the "how long" magnitude (which is what alarms and SLOs
  threshold against).
- **Cardinality**: with the filter on, only 0–1 of the 5 duration series per
  table is actually emitted at any given scrape (the currently active state, if
  it has exceeded its threshold). The 5 indicators always emit 5 series per
  table (1 hot + 4 cold); on community baseline they are *worse* than gated
  durations.
- **Alarm coverage**: keeping all 5 durations covers the previous
  `committing`/`planning` blind spots (a stuck commit is a real production
  incident class). Keeping only `pending`/`executing` indicators leaves these
  blind spots open.

Verdict:

- **MUST KEEP — O2 (`status_pending_duration`), O3 (`status_planning_duration`),
  O4 (`status_executing_duration`), O5 (`status_committing_duration`)**
  (4 metrics): the four active-stage status durations, gated dynamically by
  the value-based filter. Operators tune the per-state thresholds (e.g.
  `pending = 30min`, `committing = 5min`) to express their alarm policy
  directly in config.
- **DROP — O1 (`status_idle_duration`)**: `idle` is the steady-state of a
  healthy table; per-table idle duration emits no alarm signal and only
  inflates per-table cardinality. Retained under `legacy` for backward
  compatibility; available via `custom` for operators who still want the
  gauge.
- **DROP — O6, O7, O8, O9, O10** (5 metrics): all 5 `status_in_*` indicators
  are subsumed by the corresponding duration gauges and add no information
  under the value-based filter. They remain registered under `legacy` for
  backward compatibility.

### 3.4 Group S (Per-table Process Counters) — O11..O18

This group counts optimizing processes since AMS start (8 counters: total + failed for
all / minor / major / full).

- **MUST KEEP — O12 (`process_failed_count`)**: the canonical fail-count alarm source.
- **OPTIONAL — O11 (`process_total_count`)**: total throughput, useful for SLO dashboards.
- **DROP — O13..O18** (6 counters): minor/major/full × total/failed. The breakdown is
  better expressed as a `type` label on a single counter (a label-based refactor is
  out of scope here; for now they are redundant with O11/O12 + group-level views).

### 3.5 Group T (Per-table Last-Optimization Freshness) — O19..O23

This group answers **"how long since the table was successfully optimized?"**.

- **MUST KEEP — O22 (`since_last_optimization_mills`)**: freshness alarm source.
- **DROP — O23 (`lag_duration_mills`)**: data freshness is already covered at
  the group level via `optimizer_group_pending_tables`; the per-table
  `lag_duration` gauge therefore adds no exclusive alarm signal under the
  recommended/minimal profiles. Retained under `legacy` for backward
  compatibility; available via `custom` for operators who still want the
  per-table gauge.
- **DROP — O19, O20, O21** (3 gauges): minor/major/full breakdowns; O22 already returns
  `min(O19, O20, O21)`.

### 3.6 Group U (Per-table Summary) — S1..S15

This group captures table physical shape. Cardinality is per-table, so trimming has
high leverage. The verdict here is governed by a simple operational principle:

> **AMS metrics exist to monitor table health (i.e. whether a table needs to be
> optimized), not table capacity.** `*_delete_*` files are the dominant driver of
> read amplification and the trigger of minor / major / full compaction; the
> aggregated `health_score` is the AMS-computed summary signal that operators
> read first. Capacity attributes (total / data files, sizes, records, snapshots)
> are obtainable via the AMS REST API, the catalog (HMS / Iceberg), or the file
> system, and therefore add no exclusive signal to the Prometheus surface.

- **MUST KEEP — S3 (`equality_delete_files`), S4 (`position_delete_files`),
  S5 (`dangling_delete_files`), S8 (`equality_delete_files_size`),
  S9 (`position_delete_files_size`), S12 (`equality_delete_files_records`),
  S13 (`position_delete_files_records`), S15 (`health_score`)** (8 metrics):
  the 7 raw delete-related signals plus the aggregated health score. These are
  the numbers that decide whether a table is read-amplified and whether AMS
  should schedule it for optimize.
- **DROP — S1 (`total_files`), S2 (`data_files`), S6 (`total_files_size`),
  S7 (`data_files_size`), S10 (`total_records`), S11 (`data_files_records`),
  S14 (`snapshots`)** (7 metrics): capacity attributes. They are exposed by
  the AMS REST API and the underlying catalog, so dropping them from the
  Prometheus surface does not reduce observability — it only reduces the
  per-table cardinality budget.

> **Profile mapping.** `recommended` registers all 8 KEEP metrics. `minimal`
> registers only the 7 raw delete signals (drops `health_score` on top of the
> KEEP set, since the largest deployments tend to inspect raw signals directly).
> `legacy` keeps the full 15 metrics for backwards compatibility. See §4.4 for
> the exact profile table.

### 3.7 Group V (Per-table Orphan Cleaning) — C1..C4

- **OPTIONAL — C1, C2** (`orphan_content_file_cleaning_count`,
  `orphan_metadata_file_cleaning_count`): used to verify orphan cleaning is making
  progress. **Off-by-default in `recommended` and `minimal`** — see rationale below;
  retained on-by-default only in `legacy`, and available on demand via `custom`.
- **DROP — C3, C4** (`expected_*` counts): a debug-only counter; keep the runtime
  `inc()` call but don't register it to the registry.

> **Rationale for trimming C1/C2 from `recommended`/`minimal` (2026-06-01).**
> `OrphanFilesCleaningExecutor` runs at most once per day per table
> (`isCleanOrphanEnabled` + 24 h interval). For 99.99% of Prometheus scrape windows the
> two counters return the same constant value, while the **same `expected` and
> `deleted` numbers are already emitted as INFO logs** by `IcebergTableMaintainer`:
>   - `clearInternalTableContentsFiles`: `Deleted {finalDeleted}/{finalExpected} orphan content files for table {}`
>   - `clearInternalTableMetadata`: `Deleted {deleted}/{filesToDelete.size()} metadata files for table {}`
> So the per-table cardinality (2 × #tables) buys no additional signal in the typical
> profile; operators who need a real-time counter can re-enable them through `legacy`
> (one-line rollback) or `custom`+`metric.orphan.fields`.

### 3.8 Verdict Summary

| Group | Total | KEEP | OPTIONAL | DROP |
|---|---|---|---|---|
| P (process) | 8 | 8 | 0 | 0 |
| Q (group) | 10 | 8 | 2 | 0 |
| R (status) | 10 | 4 | 0 | 6 |
| S (process counter) | 8 | 1 | 1 | 6 |
| T (last-opt time) | 5 | 1 | 0 | 4 |
| U (summary) | 15 | 8 | 0 | 7 |
| V (orphan) | 4 | 0 | 2 | 2 |
| **Total** | **60** | **28** | **5** | **27** |

> Recommended default profile (see §4.4) registers the 28 KEEP metrics; the 5
> OPTIONAL metrics (Q's planing/idle, S's `process_total_count`, V's 2 orphan
> counters) can be opted in via `legacy` or `custom`; the 26 DROP metrics are
> permanently off unless explicitly enabled for diagnostics. KEEP for group R
> is gated at runtime by the value-based filter — see §3.3.

## 4. Whitelist Mechanism Design

This chapter specifies how the trimming is delivered as a code change. The mechanism
must satisfy two design constraints:

1. **Backwards compatible**: an operator who relies on today's full set must be able to
   restore it with a single config change.
2. **Surgical**: the change must not move metric definitions, rename them, or modify
   tag schemas — only their *registration* is gated.

### 4.1 Architecture

```
+-----------------------------+    reads    +-------------------------+
| amoro.metric.* config keys  |------------>| MetricFilterConfig      |
| (AmoroManagementConf)       |             |  - per-class field set  |
+-----------------------------+             |  - allowField(class, f) |
                                            +-----------+-------------+
                                                        |
                       used by                          |
   +----------------------+   +----------------------+  |
   | TableOptimizingMet.  |<--+                      |<-+
   | TableSummaryMetrics  |<--| maybeRegister(...)   |
   | TableOrphanFilesM.   |<--| only registers when  |
   | OptimizerGroupMet.   |<--| field is allowed     |
   +----------------------+   +----------------------+
```

- A new singleton `MetricFilterConfig` is loaded from `AmoroManagementConf` at AMS
  startup.
- Each existing metric class declares **field-name string constants** for every
  metric and replaces direct `registerMetric(...)` calls with `maybeRegister(filter,
  fieldName, ...)`.
- The internal counter / gauge instances themselves are still constructed (cheap;
  hot-path code calls them unconditionally). Only the **MetricRegistry registration**
  is gated.

### 4.2 Configuration Schema

Add the following keys to `AmoroManagementConf`:

| Key | Type | Default | Meaning |
|---|---|---|---|
| `metric.profile` | enum (`recommended`, `legacy`, `minimal`, `custom`) | `recommended` | Pre-baked profile selector. |
| `metric.optimizing.fields` | list<string> | profile-driven | Whitelist of fields in `TableOptimizingMetrics`. |
| `metric.summary.fields` | list<string> | profile-driven | Whitelist of fields in `TableSummaryMetrics`. |
| `metric.orphan.fields` | list<string> | profile-driven | Whitelist of fields in `TableOrphanFilesCleaningMetrics`. |
| `metric.optimizer-group.fields` | list<string> | profile-driven | Whitelist of fields in `OptimizerGroupMetrics`. |

Profile semantics:

- `recommended` (default): registers exactly the **KEEP** set from §3.8 (26 metrics).
- `legacy`: registers everything that was registered before this change (60 metrics);
  used to roll back behaviour without redeploying.
- `minimal`: registers an even tighter subset useful for very high-cardinality
  deployments — see §4.4.
- `custom`: respects the four `*.fields` lists verbatim; an empty list means "register
  none from that class".

If `metric.profile` ≠ `custom`, the four list keys are ignored.

### 4.3 Field-Name Constants

Each metric class adds `public static final String F_<NAME> = "<name>"` constants —
one per `MetricDefine`. The string value is the part **after** the source-class
prefix, e.g.

```java
// In TableOptimizingMetrics.java

public static final String F_STATUS_IN_EXECUTING = "status_in_executing";
public static final String F_PROCESS_FAILED_COUNT = "process_failed_count";
public static final String F_SINCE_LAST_OPTIMIZATION = "since_last_optimization";
public static final String F_LAG_DURATION = "lag_duration";
// ... and so on for all 23 metrics in this class
```

> The full constant list per class is generated mechanically from §2 — implementer
> just mirrors the metric-name suffixes.

#### 4.5.2 Metric class change pattern (example: `TableOptimizingMetrics`)

```java
private static final MetricFilterConfig FILTER = MetricFilterConfig.current();

@Override
public void registerMetrics(MetricRegistry registry) {
  if (globalRegistry != null) return;

  maybeRegister(registry, F_STATUS_IN_PENDING,
      TABLE_OPTIMIZING_STATUS_IN_PENDING, new IsInStatusGauge(STATUS_PENDING));
  maybeRegister(registry, F_STATUS_IN_EXECUTING,
      TABLE_OPTIMIZING_STATUS_IN_EXECUTING, new IsInStatusGauge(STATUS_EXECUTING));
  maybeRegister(registry, F_PROCESS_FAILED_COUNT,
      TABLE_OPTIMIZING_PROCESS_FAILED_COUNT, processFailedCount);
  maybeRegister(registry, F_SINCE_LAST_OPTIMIZATION,
      TABLE_OPTIMIZING_SINCE_LAST_OPTIMIZATION, new LastOptimizingDurationGauge());
  maybeRegister(registry, F_LAG_DURATION,
      TABLE_OPTIMIZING_LAG_DURATION, new OptimizingLagDurationGauge());
  // ... all other 18 metrics, gated identically ...

  globalRegistry = registry;
}

private void maybeRegister(MetricRegistry registry, String field,
                           MetricDefine define, Metric metric) {
  if (FILTER.allowOptimizing(field)) {
    registerMetric(registry, define, metric);
  }
}
```

The same pattern is applied to `TableSummaryMetrics`, `TableOrphanFilesCleaningMetrics`,
and `OptimizerGroupMetrics`.

In the AMS startup path (where `AmoroManagementConf` is parsed), call
`MetricFilterConfig.init(conf)` *before* any metric class is instantiated. The classes
read the singleton via `MetricFilterConfig.current()`.

## 5. Quantitative Comparison & Savings

This chapter projects the impact of the three profiles, holding cardinality constant
at 100k tables and 10 optimizer groups. Per-metric memory is the empirically observed
~36 bytes (MetricKey + tag map + atomic counter wrapper).

Per-table figures are reported **at the whitelist level** (how many fields are
allowed to register) and **at the runtime level** (how many series are actually
exposed when the value-based filters `metric.optimizing.skip-zero-status` and
`metric.summary.skip-zero-deletes` are turned on, which is the recommended
operating mode for `recommended` / `minimal`).

| Profile | Process (P) | Group (Q) | Per-table whitelist (R+S+T+U+V) | **Total registered (whitelist)** | Per-table effective (filters on) | Approx. memory (filters on) |
|---|---:|---:|---:|---:|---:|---:|
| `legacy` (today) | 8 + 2·#GCs ≈ 12 | 10 × 10 = 100 | (21 + 15 + 4) × 100k = 4,000,000 | **~4,000,112** | n/a (filters off by design) | ~144 GB |
| `recommended` | ~12 | 8 × 10 = 80 | (7 + 8 + 0) × 100k = 1,500,000 | **~1,500,092** | (≤3 R + ≤8 U + 0 V) ≈ 7–10 / table | ~26–38 GB |
| `minimal` | ~12 | 5 × 10 = 50 | (5 + 7 + 0) × 100k = 1,200,000 | **~1,200,062** | (≤2 R + ≤7 U + 0 V) ≈ 6–9 / table | ~22–32 GB |

> **Per-table whitelist breakdown:**
> - R+S+T (TableOptimizing): 7 in `recommended` (4 active-stage status
>   durations — `status_idle_duration` excluded because `idle` is the healthy
>   steady-state — + `process_total_count` + `process_failed_count` +
>   `since_last_optimization`; `lag_duration` is excluded because data
>   freshness is already covered at the group level via
>   `optimizer_group_pending_tables`); 5 in `minimal` (drops
>   `process_total_count`, `since_last_optimization` and `lag_duration` on
>   top of `recommended` — see Revision 2026-06-02; the `lag_duration` drop
>   is now covered by the `recommended` rebase).
> - U (TableSummary): 8 in `recommended` (7 raw delete signals + `health_score`);
>   7 in `minimal` (drops `health_score`).
> - V (TableOrphan): 0 in both (trimmed 2026-06-01; available via `legacy` or
>   `custom`).
>
> **Per-table effective breakdown (filters on):**
> - R: of the 4 active-stage status durations only the currently active
>   state may be emitted (and only when it exceeds its per-state threshold),
>   so 0–1 series per table; plus the 3 always-on non-status fields (S+T,
>   `process_total_count` + `process_failed_count` + `since_last_optimization`)
>   → ≤3 per table from R+S+T in `recommended`. In `minimal` the 3 non-status
>   fields shrink to 1 (just `process_failed_count`, since
>   `process_total_count`, `since_last_optimization` and `lag_duration` are
>   all dropped), so ≤2 per table from R+S+T.
> - U: with `skip-zero-deletes=true`, only delete fields with > 0 value are
>   emitted; for non-keyed tables (60–80% of typical fleets) this is 0; for
>   keyed tables the upper bound is 7 raw signals + `health_score` =
>   8 (`recommended`) or 7 (`minimal`).

**Savings vs `legacy`** (whitelist level):

- `recommended`: −60% metric count, −60% memory.
- `minimal`: −70% metric count, −70% memory.

**Savings vs `legacy`** (runtime level with both value-based filters on):

- `recommended`: −70% to −79%, depending on the keyed-table ratio and the
  fraction of tables actually stuck in a non-idle state above threshold.
- `minimal`: −76% to −83%, same drivers (improvement vs prior −72% to −80%
  comes from dropping `since_last_optimization` and `lag_duration` — both
  always-on per-table gauges that were not gated by any value-based filter).

Beyond the heap, downstream effects scale with the same factor:

| Effect | legacy | recommended | minimal |
|---|---|---|---|
| `/metrics` Prometheus scrape size | 100% | ~33% | ~28% |
| Prometheus storage ingest | 100% | ~33% | ~28% |
| AMS scrape latency | 100% | ~33% | ~28% |

> No information is lost in `recommended` for **any** read-amplification or
> optimize-trigger alert, because every dropped metric is either (a) the
> constant inverse of a kept metric (`status_in_idle`), (b) the per-type
> breakdown of an aggregate counter we keep (`process_failed_count` vs
> `minor_failed_count`), (c) a debug counter (`expected_*`), or (d) a
> capacity attribute already exposed by the AMS REST API and the underlying
> catalog (`total_files`, `data_files`, `snapshots`, ...).
