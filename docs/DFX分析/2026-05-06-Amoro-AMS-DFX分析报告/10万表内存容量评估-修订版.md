## Overview — 结论修订

### v1 遗漏了什么

v1 估算表层静态内存：TableRuntime + Metric = ~2.8 GB。**这只是冰山尖。**

v2 增补的 7 大类遗漏（**合计足以把实际堆占用推到 30-60 GB 级别**）：

| 类别 | v1 漏掉的原因 | v2 估算（10 万表，典型负载）|
|---|---|---|
| **A. Plan 阶段文件全量物化** | 只想着 TaskRuntime 骨架，漏了 `AbstractPartitionPlan` 的 3 个大 Map 和 `partitionPlanMap` + `needOptimizingPlanMap` 双份引用 | 单表 plan 瞬时 **15-150 MB**，10 并发 plan = **150 MB - 1.5 GB** |
| **B. Iceberg BaseFile 真实大小** | 按 500 B 算，实际字段有 **6 个 column-stats Map** | **1.5-3 KB / DataFile**，10 万表 × 平均 100 文件 = **1500-3000 万对象 × 2KB = 30-60 GB 常驻** ⚠️ |
| **C. 同一批 DataFile 在内存中多份引用** | plan → taskMap → TaskFilesPersistence → Thrift OptimizingTask 一份接一份 | **3-5× 放大系数** |
| **D. 已完成 process 延迟清理 + MixedTable 悬挂引用** | 假设 process commit 后立即 GC | 每 task 拴住一个 MixedTable → iceberg Table → FileIO → HadoopConfiguration 10+ MB |
| **E. Dashboard 的 `selectTableRuntimeMetas` 全量拉取 + JSON 反序列化** | 只估算 "扫表" 临时对象 | **200-500 MB** 每 3min 峰值 + 旧 List 延迟 GC 叠加 |
| **F. Overview `allTopTableItem` 全量拷贝** | 以为是 top-N，实际是 "全量" + 每次查询 `ImmutableList.copyOf` | **15 MB 常驻 × 调用次数放大** |
| **G. 无界线程池 × 多处** | 没扫线程池配置 | `CachedThreadPool` × 2 处（`DefaultOptimizingService:136`, `AmoroServiceContainer:395`），线程栈 1MB/thread，高峰可达 **GB 级** |

### v2 修订后的内存估算

| 场景 | v1 估算 | v2 估算 | 差距 |
|---|---|---|---|
| 稳态（表全部空闲，无 plan 无 execute）| 2.8 GB | **5-8 GB** | 2-3× |
| 中等负载（10% plan + 10% execute）| 5.5 GB | **15-25 GB** | 3-5× |
| 高峰（30% 活跃 + Prometheus 刮取 + Overview 刷新）| 9 GB | **30-45 GB** | **3-5×** |
| 极限（大表 plan 爆发 + 并发 completeTask 100 MB）| 24 GB | **60+ GB** | 2.5× |

**⚠️ 关键提醒**：如果你的生产集群里有**小文件爆炸的 Iceberg 表**（单表 > 10 万文件），**单表 plan 就可能吃掉 1-2 GB**。10 万表里哪怕只有 10 张这样的"毒瘤表"，就足以把 AMS 打爆。

## 1. Plan 阶段内存爆炸（v1 最大遗漏）

### 1.1 `AbstractOptimizingEvaluator.partitionPlanMap` — 全分区 evaluator

**证据**：`amoro-format-iceberg/src/main/java/org/apache/amoro/optimizing/plan/AbstractOptimizingEvaluator.java:67`

```java
protected Map<String, PartitionEvaluator> partitionPlanMap = Maps.newHashMap();
```

- `initPartitionPlans()` 在 `AbstractOptimizingEvaluator.java:118-147` 对 `FileScanTask iterator` 全量 for-loop，每个文件调 `evaluator.addFile()`
- `needOptimizingPlanMap`（`:142-146`）是 `partitionPlanMap` 的子集拷贝—— **两份同时持有 evaluator 引用**

### 1.2 `AbstractPartitionPlan` 的 3 个大 Map

**证据**：`amoro-format-iceberg/src/main/java/org/apache/amoro/optimizing/plan/AbstractPartitionPlan.java:61-76`

```java
protected final Map<DataFile, List<ContentFile<?>>> rewriteDataFiles;
protected final Map<DataFile, List<ContentFile<?>>> undersizedSegmentFiles;
protected final Map<DataFile, List<ContentFile<?>>> rewritePosDataFiles;
protected final Set<String> reservedDeleteFiles;
```

每个 Map entry **持有 DataFile + 其关联的所有 delete files**。分区文件多的表，单个分区就可能堆几万个 DataFile。

### 1.3 Plan 完成后**不是立即释放**，而是被 `tasks` 列表持续引用

**证据**：
- `AbstractOptimizingPlanner.java:55` `protected Map<String, AbstractPartitionPlan> actualPartitionPlans`
- `OptimizingQueue.planInternal()` （`OptimizingQueue.java:329`）调用 planner → `planner.tasks` → 每个 task 是 `RewriteStageTask`，`task.input = new RewriteFilesInput(...)`

### 1.4 Iceberg `BaseFile` 实际大小（**v1 严重低估！**）

**证据**：反编译 `iceberg-core-1.7.1.jar` 拿到 `BaseFile.class` **24 个字段**：

```
private Types$StructType partitionType;
private Long fileOrdinal;
private String manifestLocation;       ← cosn:// 长路径 ~150 B
private int partitionSpecId;
private FileContent content;
private String filePath;                ← cosn:// 长路径 ~200 B
private FileFormat format;
private PartitionData partitionData;
private Long recordCount;
private long fileSizeInBytes;
private Long dataSequenceNumber;
private Long fileSequenceNumber;
private Map<Integer, Long> columnSizes;        ⚠ per-column stats
private Map<Integer, Long> valueCounts;        ⚠ per-column stats
private Map<Integer, Long> nullValueCounts;    ⚠ per-column stats
private Map<Integer, Long> nanValueCounts;     ⚠ per-column stats
private Map<Integer, ByteBuffer> lowerBounds;  ⚠ per-column stats
private Map<Integer, ByteBuffer> upperBounds;  ⚠ per-column stats
private long[] splitOffsets;
private int[] equalityIds;
private byte[] keyMetadata;
private Integer sortOrderId;
private transient Schema avroSchema;
```

**尺寸推算**（有 50 列的普通 Iceberg 表）：

| 字段 | 大小 |
|---|---|
| 基础头 + 原生字段 | ~150 B |
| `filePath` + `manifestLocation` 字符串 | ~350 B |
| 6 个 column-stats Map × 50 entry × (40B entry + 24B Long/48B ByteBuffer) | **~1.8 KB** |
| `splitOffsets long[]` | ~80 B |
| `partitionData` | ~100 B |
| **合计** | **~2.5 KB / DataFile** |

**10 万表 × 100 文件平均 = 1000 万 DataFile × 2.5 KB = 25 GB 纯 DataFile 常驻**（只有在它们被 `AbstractPartitionPlan` 引用的时间窗内）

> **v1 按 500 B 估算 → 实际 2.5 KB → 低估 5×**。这就是差距来源最大的一块。

### 1.5 `RewriteFilesInput` 持有 4 个数组 + MixedTable 引用

**证据**：`amoro-format-iceberg/src/main/java/org/apache/amoro/optimizing/RewriteFilesInput.java:37-41`

```java
private final DataFile[] rewrittenDataFiles;
private final DataFile[] rePosDeletedDataFiles;
private final ContentFile<?>[] readOnlyDeleteFiles;
private final ContentFile<?>[] rewrittenDeleteFiles;
private final MixedTable table;   ⚠ 致命：每个 task 拴一个 MixedTable
```

- 每个 `RewriteStageTask.input = RewriteFilesInput`，**这个 input 在 TaskRuntime 里常驻直到 task 完成**
- `MixedTable` 引用一整个 iceberg `Table` + `FileIO` + `HadoopConfiguration`（Configuration 通常 5-10 MB，包含所有 core-site/hdfs-site key-value + XML DOM）

### 1.6 内存估算（Plan 阶段）

| 场景 | 单表 plan | 10 并发 plan |
|---|---|---|
| 普通表（100 分区 × 100 文件 = 1 万 DataFile） | 25 MB | **250 MB** |
| 大表（1000 分区 × 1000 文件 = 100 万 DataFile）| 2.5 GB | **25 GB** ⚠️ |
| 小文件表（10 万 fragment files） | 250 MB | **2.5 GB** |

**10 万表里只要有 1-10 张大表同时在 plan，内存就会轻松突破 10 GB**。

## 2. 同一批 DataFile 在内存中的多份引用（3-5× 放大）

一次 Plan/Execute/Commit 流程中，同一个 DataFile 对象/其序列化字节会被**以下地方同时持有**：

| 持有者 | 位置 | 持有形式 |
|---|---|---|
| 1. `AbstractPartitionPlan.rewriteDataFiles` | `AbstractPartitionPlan.java:61` | `DataFile` 引用 |
| 2. `RewriteStageTask.input.rewrittenDataFiles` | `RewriteFilesInput.java:37` | `DataFile[]` 引用（可能与 1 共享）|
| 3. `TaskFilesPersistence.persistTaskInputs` 序列化缓冲 | `TaskFilesPersistence.java` | Kryo + gzip 序列化后的 byte[]（per task ~100 KB-1 MB） |
| 4. DB 表 `optimizing_task_file` 的 BLOB | mapper | 持久化到 DB（内存里不占了）|
| 5. `OptimizingTask.input` (Thrift 下发) | 自动生成的 thrift 类 | ByteBuffer 二次序列化 |
| 6. `DefaultOptimizingState` 的 metric / summary | `TableSummaryMetrics` | 长引用到 taskRuntime 间接保留 |

**放大系数**：同一批 DataFile 字节在内存里至少 **3 份**（1+2 共享 + 3 + 5），plan 完成前 4 份，commit 前 5 份。

> **v1 没有考虑这个放大。按 DataFile 真实大小 2.5 KB × 3-5 倍放大 = 7-12 KB 有效占用**。1000 万 DataFile × 10 KB = **100 GB 级峰值**（同一时刻）。

## 3. 已完成 process 延迟清理 + MixedTable 悬挂引用

### 3.1 清理点

**证据**：`amoro-ams/src/main/java/org/apache/amoro/server/optimizing/OptimizingQueue.java:186 + 194`

```java
tableQueue.removeIf(process -> process.getProcessId() == optimizingProcess.getProcessId());
```

- `clearProcess` 在 `OptimizingQueue.java:791` 被异步 future 调用
- **但这只清理 `tableQueue` 里的 Process 引用，Process 内部的 `taskMap`、`RewriteFilesInput`、`MixedTable` 引用如果有未完成的 TaskRuntime 还拴着，就不会被 GC**

### 3.2 MixedTable 生命周期

- 每个 `RewriteFilesInput.table = MixedTable`
- `MixedTable` 引用 iceberg `BaseTable` + `FileIO`
- `InternalCatalogImpl.java:248-258` 用 `Caffeine.newBuilder().weakKeys()` 做 FileIO closer — **只在 key 被 GC 后才 close**
- 只要 `RewriteStageTask` 强引用 MixedTable，**FileIO 不会 close**

### 3.3 内存估算

| 场景 | 单对象 | 10 万表规模 |
|---|---|---|
| `MixedTable` 本身 | ~1 KB | N/A |
| iceberg `BaseTable` 含 `TableOperations`、`TableMetadata` | ~5-10 KB（snapshot 列表 + schema）| — |
| `HadoopConfiguration`（AMS 创建 catalog 时共享）| **5-10 MB 共享** | ~10 MB 总 |
| `FileIO`（S3/COS client）| ~1-5 MB（含 HTTP client pool）| 每 catalog 1 份 |
| **100 个活跃 task × 间接拴 1 个 catalog 的 context** | — | **持久占用 ~50 MB** |

## 4. Dashboard Overview 的隐藏大坑

### 4.1 `OverviewManager.refreshTableCache()` 每 3 分钟执行

**证据**：`amoro-ams/src/main/java/org/apache/amoro/server/dashboard/OverviewManager.java:170-237`

```java
List<TableRuntimeMeta> allMetas =
    getAs(TableMetaMapper.class, TableMetaMapper::selectTableRuntimeMetas);
```

- SQL：`TableMetaMapper.java:386-462` 是 **4 表 JOIN + 无 LIMIT**（`table_runtime` × `table_identifier` × `table_process` × `optimizing_process_state`）
- 每行返回 `TableRuntimeMeta`：
  - `tableConfig` — **JSON 反序列化** → 5-10 个嵌套 config 对象，~1-2 KB
  - `pendingInput` + `tableSummary` — **2 份 JSON 反序列化** → 含 `partitions` Map，~1-5 KB/份
  - `fromSequence` + `toSequence` — `Map<String, Long>`，分区多的表可能 ~1 KB/份

**单 `TableRuntimeMeta` ≈ 5-10 KB**

### 4.2 10 万表规模估算

| 刷新阶段 | 内存占用 |
|---|---|
| SQL 返回 10 万行结果集（JDBC 缓冲）| **500 MB - 1 GB** |
| JSON 反序列化 10 万 × 4 个 JSON 字段 | **持续分配 200-500 MB（young gen 压力）** |
| 构造 `allTopTableItem` List 10 万 item | 15 MB 常驻 |
| 旧 `allTopTableItem` + 新 list **同时存在窗口** | 30 MB |
| 旧 `catalogSummaryMap.optimizingSummariesPerHour` 累积（720 条/catalog）| 长期增长 |

**3 分钟一次刷新，每次峰值 500 MB-1 GB**。Prometheus 刮取 + Overview 刷新碰到一起 = 1-2 GB 瞬时分配。

### 4.3 `allTopTableItem` 其实是 "all"，不是 "top"

**证据**：`OverviewController.java:63-108`

```java
getTopTables() {
    return overviewManager.getAllTopTableItem()
        .stream().sorted(...).limit(limit=默认10)...
}
```

- `getAllTopTableItem()` 在 `OverviewManager.java:114` 返回 `ImmutableList.copyOf(allTopTableItem)` — **全量深拷贝**
- 前端每次切换排序都会调用一次 → 每次再分配 15 MB

## 5. 无界线程池

### 5.1 `DefaultOptimizingService.planExecutor`

**证据**：`amoro-ams/src/main/java/org/apache/amoro/server/DefaultOptimizingService.java:136`

```java
planExecutor = Executors.newCachedThreadPool(...);
```

- **CachedThreadPool 没有上限**，只要 plan 任务提交得比执行完成快，线程数就无限增长
- 虽然实际并发由 `maxPlanningParallelism` 控制（`AmoroManagementConf.java` 找配置），但**如果配置没设上限或很大**，线程池会起几十/上百个线程
- 每线程默认 stack 1 MB（`-Xss1m`），**100 plan 线程 = 100 MB 栈内存**
- 每 plan 线程内部分配的 Iceberg FileScanTask iterator 缓冲 + DataFile List，~50-200 MB

**10 plan 线程并发 → 500 MB-2 GB**（这是线程栈 + 堆上 plan buffer）

### 5.2 其他线程池

**证据**：
- `AmoroServiceContainer.java:395` `Executors.newCachedThreadPool(...)` - Thrift OptimizingService executor 也是 **无界**
- `PeriodicTableScheduler.java:60,72` - 2 个 scheduledThreadPool
- `TableController.java:127` - dashboard 的 scheduledThreadPool
- `AmoroServiceContainer.java:377` - Thrift TableService 是 fixed

## 6. 隐藏长引用链（v1 没考虑）

### 6.1 `DefaultTableRuntime.processContainerMap`

**证据**：`DefaultTableRuntime.java:52 + :141`

```java
private final Map<Action, TableProcessContainer> processContainerMap = Maps.newConcurrentMap();
// ...
private final Map<Long, AmoroProcess<? extends TableProcessState>> processMap
```

- 每个 action（OPTIMIZING、EXPIRE_SNAPSHOTS、EXPIRE_DATA、EXPIRE_BLOCKER 等）一个 container
- container 内部的 `processMap` 保存所有进行中的 process
- **清理逻辑在哪里？** 如果 process 完成/失败后没有从 `processMap` remove，会累积

### 6.2 `CopyOnWriteArrayList<TaskQuota>` 永久累积

**证据**：`DefaultOptimizingState.java:76`

```java
private final List<TaskRuntime.TaskQuota> taskQuotas = new CopyOnWriteArrayList<>();
```

- `addTaskQuota()` 在 `DefaultOptimizingState.java:449` 无限 append
- 搜索清理逻辑：`AmoroManagementConf.java:299` 有 `runtime-data-expire-interval-hours` 配置，但消费点在**定时 job** 里，30 分钟-1 小时清理一次
- **如果 AMS 活跃持续，30 分钟窗口内每表累积几百-几千个 TaskQuota，10 万表 × 1000 = 1 亿对象 × 80 B = 8 GB**（极端情况）
- 正常每表几十个 TaskQuota：10 万 × 50 × 80 B = **400 MB**

### 6.3 `CatalogSummary.optimizingSummariesPerHour` per-catalog 720 条

**证据**：`OverviewManager.java:223-229`（保留旧值逻辑）

- 每 catalog 保留 30 天 × 24 小时 = **720 条**，永不清除直到 catalog 删除
- 每条 ~100 B，每 catalog 720 × 100 B = 72 KB
- 100 catalog = 7.2 MB（可控）

## 8. 为什么实际生产 > 理论估算（总结因果）

| 观测现象 | 原因（v2 发现） |
|---|---|
| AMS 重启后 1-2 小时稳步上涨到 10 GB | Overview 每 3 min 刷新 + `TaskQuota` 累积（§4.1, §6.2）|
| 某些时刻突然涨 3-5 GB | 单张大表在 plan（§1，PartitionPlan + DataFile 全量物化）|
| Prometheus 刮取时间 young GC 频繁 | 340 万 metric 对象渲染瞬时分配（v1 §2.4 已述）|
| 某个 catalog 挂了以后 AMS 内存不释放 | MixedTable + HadoopConfiguration 悬挂引用（§3）|
| 重启恢复时内存飙到 8 GB | `selectTableRuntimeMetas` 一次性拉 10 万行 + JSON 反序列化（§4.1）|
| 长时间运行后 metric 看起来正常但 GC 压力大 | `TaskQuota CopyOnWriteArrayList` 累积（§6.2）|
| 高峰期内存忽然翻倍 | 同批 DataFile 在 plan → persist → thrift 三份引用（§2）|

## 9. v2 新增的 P0 建议

v1 给了 10 条建议，v2 基于新发现补充 5 条：

### 9.1 【P0】限制并发 plan 的数量 + 切换成**流式扫描**

- 现状：Plan 阶段 `FileScanTask iterator` 被 `for-loop` 消费后所有 DataFile 对象落地到 `partitionPlanMap`（§1.1）
- 改动方向：Plan 分批处理 + 超过阈值先 flush partial task，不要全量在内存攒
- 或：限制 `maxPlanningParallelism` ≤ 3（10 万表场景下即使 3 路 plan 也可能吃 30 GB）

### 9.2 【P0】`TaskFilesPersistence` 的 Kryo 序列化结果**不要留 byte[] 缓冲**

- 现状：每次持久化 TaskInput 要把 `DataFile[]` 先 Kryo 序列化成 byte[]，再 gzip，再插 DB
- 改动方向：stream 到 DB `INSERT INTO ... (blob_field) VALUES (?)` 的 `setBinaryStream`，不要生成中间 byte[]

### 9.3 【P0】`OptimizingQueue.tableQueue.removeIf` 后**显式 null 掉 process 内部字段**

- 现状：`clearProcess` 只从 queue 移除 process，process 对 taskMap、RewriteFilesInput、MixedTable 的引用没断
- 改动方向：清理前调 `process.dispose()` 把内部字段置 null，让 GC 可回收

### 9.4 【P1】`OverviewManager.refreshTableCache` 改成**分批 SELECT**（按 catalog 分页）

- 现状：一条 4-表 JOIN + 无 LIMIT 拉 10 万行
- 改动方向：按 `catalog_id` 分页查询（每批 1000-5000 行），流式聚合

### 9.5 【P0】Iceberg `Table` / `FileIO` / `HadoopConfiguration` 在 AMS 应该是**共享单例**

- 现状：每个 `MixedTable` 可能持有独立的 Configuration（~10 MB），100 活跃 task = 1 GB
- 改动方向：`HadoopConfiguration` 应在 `AmoroServiceContainer` 启动时构造一次，所有 catalog 共享引用

## 10. 一句话总结（v2）

**v1 估算 10 万表稳态 2.8 GB 是因为只看了表层骨架 + metric；实际生产 >> 这个数的真正原因是：**

1. **单个 Iceberg `DataFile` 对象真实大小 2.5 KB**（含 6 个 column-stats Map），不是 v1 假设的 500 B——**5× 低估**
2. **Plan 阶段把整张表的 DataFile 全量物化到 `AbstractPartitionPlan` 的 3 个 Map 里**，并通过 `RewriteFilesInput[]` 延续到 execute/commit，**3-5 倍引用放大**
3. 每个 task 间接拴住 `MixedTable → Table → FileIO → HadoopConfiguration`（10 MB/份），且 `Caffeine.weakKeys()` 延迟释放
4. `OverviewManager.refreshTableCache` 每 3 min 用无 LIMIT SQL 拉 10 万 `TableRuntimeMeta`（每条 5-10 KB，**全量 500 MB-1 GB**），叠加 JSON 反序列化的瞬时分配
5. `allTopTableItem` 不是 top-N 是 "all"，每次 `getTopTables` 调用 `ImmutableList.copyOf` 全量深拷贝 15 MB
6. **2 处无界 `CachedThreadPool`**（`DefaultOptimizingService:136` 和 `AmoroServiceContainer:395`），没有 concurrency cap
7. `CopyOnWriteArrayList<TaskQuota>` 每表永久累积直到定时清理

**综合 7 大类遗漏，10 万表真实内存需求是 30-60 GB，不是 v1 说的 3-10 GB**。这解释了为什么生产环境观测值远超理论估算。紧急建议：立刻把 `-Xmx` 设到 **32 GB**（中等负载安全区间），K8s `resources.limits.memory: 48Gi`，同时跟进上面 §9 的 5 条 P0 改动。
