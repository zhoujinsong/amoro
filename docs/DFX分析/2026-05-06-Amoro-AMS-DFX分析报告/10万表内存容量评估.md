## Overview — 结论先行

| 场景 | 最小堆 | 推荐堆 | 关键占用 |
|---|---|---|---|
| **稳态（表全部空闲）** | **3.3 GB** | **6 GB** | `tableRuntimeMap` (~200 MB) + 3.4M 个 metric 对象（~1.2 GB）+ Prometheus label 串（~800 MB） |
| **中等负载（10% 表在 plan/执行）** | **5.5 GB** | **10 GB** | + OptimizingProcess/TaskRuntime ≈ 800 MB + taskFiles 元数据 ≈ 1 GB |
| **高峰（30% 表+大 task）** | **9 GB** | **16 GB** | + Prometheus scrape 瞬时峰值 ~1.5 GB + 重计算 collectTasks() 分配爆发 |
| **极限（元数据巨大表，小文件爆炸）** | **12 GB** | **24 GB+** | 单个 `OptimizingTask.input`（DataFile 列表）可达 100 MB（因为 Thrift frame 已放开到 100 MB）|

**一句话**：**目前代码在默认配置下跑 10 万表至少需要 8-16 GB 堆**，其中 **metric 相关对象占了 35-40%**（约 2-4 GB），是最大的单一内存消耗项。而 Helm chart `resources: {}` 默认空（`charts/amoro/values.yaml:431`），Dockerfile 没设 `-Xmx`（`docker/amoro/Dockerfile:47-62`），**上线即 OOM 几乎是确定事件**。

下面分章节精确推导，每条都带 `file:line` 证据。

## 1. 单张表在 AMS 中的对象图

每张表在 AMS 稳态下对应一个对象树：

```
ServerTableIdentifier  ←——  [SchedulingPolicy.tableRuntimeMap / OptimizingQueue 的 map]
         │
         ├──→ DefaultTableRuntime
         │      ├── Map<Action, TableProcessContainer>   (per-action，通常 2-3 项)
         │      ├── DefaultOptimizingState
         │      │      ├── 3 个 metric 对象:
         │      │      │     · TableOptimizingMetrics         (15 个 MetricDefine)
         │      │      │     · TableSummaryMetrics            (15 个 MetricDefine)
         │      │      │     · TableOrphanFilesCleaningMetrics(4 个 MetricDefine)
         │      │      ├── CopyOnWriteArrayList<TaskQuota>    (历史配额记录)
         │      │      ├── Map<String,Long> fromSequence/toSequence  (2 个 HashMap)
         │      │      └── TableConfiguration                 (10 个字段，含嵌套 config)
         │      └── ...
         │
         └──→ MetricRegistry 里的 34 个 MetricKey + 34 个 Metric<X> 包装对象
```

### 1.1 核心证据

| 字段/容器 | 位置 | 说明 |
|---|---|---|
| `tableRuntimeMap` 主索引 | `SchedulingPolicy.java:49` `Map<ServerTableIdentifier, DefaultTableRuntime> tableRuntimeMap = new HashMap<>();` | 全量保留，无 eviction |
| `DefaultTableRuntime` 核心字段 | `DefaultTableRuntime.java:50-52` | `tableIdentifier` + `optimizingState` + `processContainerMap` |
| `DefaultOptimizingState` 核心字段 | `DefaultOptimizingState.java:72-102` | 含 **3 个 metric 对象** (`:94-96`) + `taskQuotas` (`:76`) + `fromSequence/toSequence` (`:99-100`) + `@StateField` volatile 字段 ≥ 10 个 |
| metric 注册结构 | `AbstractTableMetrics.java:17-23` | `List<MetricKey> registeredMetricKeys` + 每个 `MetricKey` 对应 `ImmutableMap<String,String>` label（catalog/database/table 三项）|
| catalog 缓存（可控） | `DefaultCatalogManager.java:65` | `CacheBuilder.newBuilder().maximumSize(100)` —— 有上限，不是内存问题 |
| `OptimizerGroupMetrics`（per-group 非 per-table）| `OptimizerGroupMetrics.java:43-77` | 固定 6 个 MetricDefine，与表数无关 |

### 1.2 字段级 JVM 内存估算（per table，稳态）

JVM 64 位 + CompressedOops + 8 字节对齐（下同）：

| 对象 | 单对象占用（含对齐） | 数量/表 | 小计 |
|---|---|---|---|
| `DefaultTableRuntime` 自身 | ~40 B | 1 | 40 B |
| `processContainerMap` (HashMap + 0-3 Entry) | ~128 B | 1 | 128 B |
| `ServerTableIdentifier` (5 个 String 引用) | **~400 B**（含 catalog/database/tableName 字符串平均 30-50 字节） | 1-2 份（map key 与内部） | 500 B |
| `DefaultOptimizingState` 自身（27 个字段） | ~200 B | 1 | 200 B |
| `TableConfiguration` + `OptimizingConfig` + `DataExpirationConfig` + `TagConfiguration` | ~400 B | 1 | 400 B |
| `CopyOnWriteArrayList<TaskQuota>`（默认空，运行期累积）| ~64 B 空 + 每个 TaskQuota ~80 B | 1 list + 0-20 个 | 64 B ~ 1.7 KB |
| `Map<String,Long> fromSequence / toSequence` | 2 × HashMap 空 ≈ 128 B | 2 | 256 B |
| `@StateField volatile long/enum` × 10+ | 对象头已算入 state 自身 | — | 0 |
| **TableSummaryMetrics**：15 个 `Counter`/`Gauge` wrapper | **每个 ~40 B** | 15 | 600 B |
| **TableOptimizingMetrics**：15 个 wrapper | 每个 ~40 B | 15 | 600 B |
| **TableOrphanFilesCleaningMetrics**：4 个 wrapper | 每个 ~40 B | 4 | 160 B |
| **34 个 MetricKey**（含 3-entry ImmutableMap label）| `MetricDefine` 引用（共享）+ `ImmutableMap<String,String>` ≈ **~200 B**（3 个 Entry × ~40 B + 引用 3 个共享 String） | 34 | **6.8 KB** |
| Prometheus 端**每个 metric 的 label 字符串拼接 cache**（如启用）| 每指标 ~60-100 B | 34 | ~2.7 KB（上限） |
| HashMap `tableRuntimeMap` Entry | ~48 B | 1 | 48 B |

**单张表稳态估算：~12 KB ~ 18 KB**（取中位 15 KB）

> **关键观察**：**约 60% 的单表内存被 metric 相关对象占用**（34 个 MetricKey + 34 个 wrapper + label 字符串）。这就是后面要专门分析的点。

### 1.3 推导到 10 万表

| 项 | 10 万表合计 |
|---|---|
| 单表对象（不含 metric）| 10⁵ × 6 KB = **600 MB** |
| metric 对象（34 × 10⁵ = **340 万个**）| 10⁵ × 7 KB = **700 MB** |
| Prometheus label 字符串 | 10⁵ × 2.5 KB = **250 MB** |
| **10 万表稳态总计** | **~1.55 GB**（仅表对象 + metric） |

### 2.2 MetricRegistry 存储模型（放大系数）

证据：`AbstractTableMetrics.java:25-39`

```java
protected void registerMetric(MetricRegistry registry, MetricDefine define, Metric metric) {
  MetricKey key =
      registry.register(
          define,
          ImmutableMap.of(
              "catalog", identifier.getCatalog(),
              "database", identifier.getDatabase(),
              "table", identifier.getTableName()),
          metric);
  registeredMetricKeys.add(key);
}
```

**每次注册产生的对象**：
1. 一个 `ImmutableMap<String,String>` 带 3 个 Entry — 约 200 B（3 × Entry ~40 B + map 自身 ~80 B）
2. 一个 `MetricKey` 对象 — 约 40 B，内部引用上面的 ImmutableMap
3. MetricRegistry 内部 Map entry — 约 48 B
4. Metric 包装对象（Gauge/Counter）— 约 40 B，含对当前 metric-value 对象的引用
5. 被 metric 包装的 AtomicLong / Supplier（Counter 通常是 AtomicLong，Gauge 通常是 Supplier）— 约 24-40 B

**每个 metric 约 ~350 B（含 label Map + MetricKey + wrapper + Entry）**。

### 2.3 10 万表的 metric 内存总账

| 对象 | 单项内存 | 数量 | 合计 |
|---|---|---|---|
| metric wrapper × `TableSummaryMetrics`（15）| ~40 B | 1.5M | 60 MB |
| metric wrapper × `TableOptimizingMetrics`（15）| ~40 B | 1.5M | 60 MB |
| metric wrapper × `TableOrphanFilesCleaningMetrics`（4）| ~40 B | 400K | 16 MB |
| `MetricKey` × 34（per table） | ~40 B | 3.4M | 136 MB |
| `ImmutableMap<String,String>` 3-entry label × 34 | ~200 B | 3.4M | **680 MB** |
| `MetricRegistry` 内部 Map Entry | ~48 B | 3.4M | 163 MB |
| 支撑 Gauge 的 `Supplier` lambda / `AtomicLong` counter | ~32 B | 3.4M | 108 MB |
| **小计（仅 metric 层）** | — | **3.4M 对象** | **~1.22 GB** |

### 2.4 Prometheus 刮取瞬时放大（P1 级风险）

当 Prometheus 抓取 `/prometheus` 端点时（`AmoroManagementConf.java:270 → PROMETHEUS_EXPORTER_PORT = 19090`）：

1. **全量序列化**所有 metric，每张表的 34 个指标要渲染成 Prometheus text 格式：
   ```
   table_summary_total_files{catalog="xx",database="yy",table="zz"} 12345
   ```
   每行约 100-150 字节。10 万表 × 34 指标 = **340 万行 × 120 B ≈ 400 MB 文本缓冲**。

2. **瞬时堆内内存峰值 +400~800 MB**（字符串拼接 + 字符拷贝），刮取频率越高、峰值越大。

3. **证据**：代码里的 `OptimizerGroupMetrics.java:128-140` 的 Gauge 在刮取时触发 `collectTasks()`（主报告 §2.2.3）全量遍历 `tableQueue`，10 万 task 时产生 10⁵ 对象的 List 分配——**这是双重放大**：metric 渲染本身就 400 MB，再加 collectTasks 分配的 List 100 MB+。

**结论：Prometheus 刮取一次，瞬时堆占用增加 500 MB - 1 GB**，在 G1/ZGC young-gen 吃紧时极易触发 Full GC 或 OOM。

### 2.5 Dropwizard/micrometer 指标基础设施的固定成本

暂未精确量化，但参考业界经验：3.4M 个指标对象在 Dropwizard `MetricRegistry` 里的 **内部 ConcurrentHashMap** 自身开销（rehash + bucket）约占总指标内存的 **15-20%**，即额外 **200-250 MB**。

## 3. OptimizingProcess / TaskRuntime 的动态放大

### 3.1 单个 TaskRuntime 内存

证据：`TaskRuntime.java:39-50`

```java
public class TaskRuntime<T extends StagedTaskDescriptor<?, ?, ?>> extends StatedPersistentBase {
  private final SimpleFuture future = new SimpleFuture();
  private final TaskStatusMachine statusMachine = new TaskStatusMachine();
  private OptimizingTaskId taskId;
  private T taskDescriptor;                     // ← 大头：含输入 DataFile 列表
  @StateField private Status status = Status.PLANNED;
  @StateField private int runTimes = 0;
  @StateField private long startTime = ...;
  @StateField private long endTime = ...;
  @StateField private long costTime = ...;
  @StateField private String token;
  @StateField private int threadId = -1;
  @StateField private String failReason;
}
```

固定开销 ~200 B（未计 taskDescriptor）。

**大头在 `taskDescriptor`**：`RewriteStageTask` 之类的任务描述符会序列化待 rewrite 的 DataFile / DeleteFile 列表。一张中等规模 Iceberg 表做 minor compaction，可能包含 100-1000 个待 rewrite 的文件，每个 DataFile 序列化 ~300 B-1 KB，单 `taskDescriptor` 可达 **100 KB-1 MB**。

### 3.2 中等负载（10% 表活跃 = 1 万张表在 plan/run）

- `OptimizingProcess`（主报告 §2.2.2 中 `OptimizingQueue.java:424`）每个持有 `Map<OptimizingTaskId, TaskRuntime<RewriteStageTask>> taskMap`
- 每个活跃表平均 5 个 task，每 task 100 KB → 每活跃表 ~500 KB
- 1 万 × 500 KB = **5 GB（!!）**

> 这个数字如果真达到，**仅活跃 task 就比稳态所有表的内存还高一倍**。实际生产中 task 不会这么大（minor compaction 通常 10 个文件以内），但**最大文件/表数量**是个**没有上限的维度**，由用户数据决定，AMS 无法自保护。

### 3.3 特殊风险：Thrift frame 放大到 100 MB 后的新 OOM 面

本 branch `dev/fix-thrift_package_len` 把 Thrift 帧上限从 16 MB 提到 100 MB。这意味着：

- Optimizer 上报 `completeTask` 时可以携带 ~100 MB 的 result（输出 DataFile 列表）
- AMS 收到后反序列化为 Java 对象，**堆内占用约 1.5-2 倍原始字节**，即 **150-200 MB per request**
- `amoro-ams` 默认 worker threads = 20（`AmoroManagementConf.java:252`），**并发 20 个大 completeTask = 3-4 GB 瞬时堆分配**

**这是一个本次 fix 连带引入的新风险**。原来 16 MB 自然卡住了最大 payload，现在放开了，需要通过其他手段限流。

## 4. 其他显著的内存消耗

### 4.1 Dashboard 后端聚合（P1）

主报告 §1 提到 Overview 每 3 min 全量扫所有表（`AmoroManagementConf.java:88` `Duration.ofMinutes(3)`）。扫描过程中把 10 万张表的元数据读入内存聚合 → 一次 Overview 刷新临时分配 **100-200 MB**。

### 4.2 `TableMetaMapper` 21 个 SQL（P2）

主报告 §4.2.2 提到所有 SQL 在注解里。其中 `listTables` 类 SQL 一次返回 10 万行 → 约 50-100 MB。

### 4.3 `scheduleTable` 排序内存（P1）

`SchedulingPolicy.java:88-99` 每次调度对 10 万 `TableRuntime` 排序，`Arrays.sort` 分配 O(N) 临时数组 — 约 **1.6 MB**（每 TableRuntime 引用 16 B），不大但每调度周期都在 young gen 分配，GC 频次会显著上升。

### 4.4 `LinkedTransferQueue tableQueue`（P2）

`OptimizingQueue.java:90` — 链表节点每个 ~48 B，10 万 process = ~5 MB。不大，但 `removeIf` O(N)（主报告 §2.2.5）。

### 4.5 `SnapshotID`/`sequence` 历史记录

`DefaultOptimizingState` 里有 `currentSnapshotId`/`lastOptimizedSnapshotId` 等 volatile long — 每个 8 B，10 个字段 × 10 万表 = 8 MB。可忽略。

### 5.1 稳态（所有表都 IDLE）

### 5.3 Prometheus 刮取瞬时峰值

每次 `/prometheus` 被刮时（假设 15 s 一次，Prometheus 默认）：

| 瞬时分配 | 估算 |
|---|---|
| 序列化 340 万指标行 text buffer | 400 MB |
| `collectTasks()` 生成 List（主报告 §2.2.3）| 100-200 MB（取决于活跃 task 数）|
| 字符串中间对象（StringBuilder 扩容、char[] 拷贝）| 200-400 MB |
| **单次刮取瞬时峰值** | **700 MB - 1 GB** |

若 Prometheus 多副本 + 频率高（5s 刮一次），峰值可叠加——**严重推荐把 scrape interval 调到 ≥30s 或在 AMS 侧 throttle**。

### 5.4 极限场景（活跃大 task 爆发）

- Thrift fix 放开到 100 MB
- 20 个 worker thread 并发 completeTask，每个 200 MB 反序列化峰值
- 叠加 Prometheus 刮取 1 GB
- **极限瞬时峰值：8-10 GB over 稳态**

**极限 -Xmx 建议：24 GB+**

## 7. 可执行建议（按 ROI 排序）

> 本章节区别于 DFX 主报告的"只指风险"原则，在内存维度给出**具体、可量化**的缓解手段。

### 7.1 立即（不改代码）

1. **设定 `-Xmx`**：Docker entrypoint 加 `JAVA_OPTS=-Xmx8g -XX:+UseG1GC -XX:MaxGCPauseMillis=200`（10 万表场景最小配置）。
2. **Helm `resources`**：
   ```yaml
   resources:
     requests:
       cpu: 4
       memory: 10Gi
     limits:
       cpu: 8
       memory: 16Gi
   ```
3. **Prometheus scrape interval ≥ 30s**（降低峰值叠加概率）。
4. **禁用部分 metric**：如果 `TableSummaryMetrics` 的业务价值低，关掉 register 能省 **~400 MB**（15/34 ≈ 44% 的 metric 内存）。需在 `DefaultOptimizingState.java:94-96` 增加 feature flag（小改动）。

### 7.2 短期（小改动，一两天）

5. **Label 字符串 intern**：把 `AbstractTableMetrics.java:29-36` 里 `identifier.getCatalog()/getDatabase()/getTableName()` 做 `String.intern()`。10 万表只有 ~20 个 catalog × ~500 个 database，intern 后 label 字符串 **从 800 MB 降到 80 MB**。
6. **ImmutableMap → 共享 key 数组**：把 `"catalog"/"database"/"table"` 三个 key 声明为 `static final String` 共享，label Map 改为定长数组（类似 Prometheus client_java 的 LabelValues），每 MetricKey 从 ~200 B 降到 ~60 B → **节省 480 MB**。
7. **分 catalog/database 分页 Overview**：主报告 §2.2.6，把全量扫改成增量刷新。

### 7.3 中期（架构改动）

8. **Metric 按需注册**：仅对"活跃的"或"异常的"表注册全量 metric；IDLE 表只注册 1-2 个核心指标。能把 metric 内存从 **1.2 GB 降到 200 MB**。
9. **TableRuntime 分层缓存**：热表（正在 optimize 的）在内存，冷表换页到 off-heap 或 DB。10 万表典型活跃度 <10%，冷表换页可省 **~500 MB**。
10. **Thrift 请求大小观测+限流**：新增 metric `thrift.request.size.histogram`，当单请求 > 50 MB 时 throttle 或拒绝。配合本 branch fix 使用。

---

## 8. 一句话总结

**10 万表规模下，当前 Amoro AMS 默认配置需要 8-16 GB 堆；其中 metric 层（`TableSummaryMetrics` 15 + `TableOptimizingMetrics` 15 + `TableOrphanFilesCleaningMetrics` 4 = 34 个指标 × 10 万表 = 340 万个 metric 对象 + 等量 3-entry ImmutableMap label）独占 1.2-1.5 GB（35-40%），是第一大内存吃货；Prometheus 刮取一次瞬时再增 700 MB-1 GB；叠加本 branch 把 Thrift frame 放到 100 MB 后的并发 worker 反序列化峰值 3-4 GB，真实极限峰值可达 24 GB+。** Docker `-Xmx` 未设 + Helm `resources: {}` 空，**生产上线即 OOM 是确定事件**——这是目前最紧急的"内存侧 P0"。ROI 最高的三个缓解动作是（1）立刻设 `-Xmx` 和 `resources`，（2）给 metric label 字符串做 `intern()`，（3）考虑对 IDLE 表只注册核心指标。
